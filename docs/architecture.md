# How the Magdaport invoice pipeline works

This page traces one supplier invoice through the pipeline, from the Gmail poll to the label on its email. It then covers what each part stores, how failures surface and recover, where the stack stops scaling, how it treats untrusted documents, and why each design choice beat its alternative.

![System architecture: Gmail feeds gmail-entry and intake-email; process-invoice saves to Postgres, files the PDF in Google Drive, writes Google Sheets rows, and labels the email; extract-invoice calls Anthropic](diagrams/architecture.svg)

Both diagrams on this page come from JSON sources in `docs/diagrams/`. From each source, [archify](https://github.com/tt-a1i/archify) renders an SVG image and an interactive HTML page with search, focus, and light and dark themes, and `AGENTS.md` lists the regeneration steps.

## Context: who uses it and where it runs

Magdaport S.A.S. is a fictional wholesale distributor in Barranquilla, Colombia, whose suppliers email it PDF invoices in Colombian pesos (COP) or US dollars. For each PDF, the pipeline does four jobs:

- extracts the invoice’s fields and line items with Claude
- checks totals, dates, and the model’s confidence, and flags a doubtful invoice for review
- files the PDF in Google Drive and lists the invoice and its items in Google Sheets
- labels the source email, then counts the invoice in a daily summary email at 18:00 Bogota time

The whole runtime is one Docker Compose project, `magdaport-invoices`:

- **n8n 2.45.6**: the workflow engine, with its port published on `127.0.0.1:5678` only
- **Postgres 17**: database `n8n` for n8n’s own data and database `app` for invoices and events
- **Redis and `n8n-worker`** (optional, `compose.queue.yaml`): queue mode, covered under scaling

The external services are Gmail, Google Drive, and Google Sheets, all under one Google account, and the Anthropic API. Claude Haiku 5.5 is the default model, and Claude Sonnet 5.5 handles retries. Because n8n polls Gmail, nothing on the internet calls in, and the stack has no tunnel.

## The nine workflows and what starts them

The pipeline is nine n8n workflows with fixed IDs from `scripts/manifest.ts`. All of them except `error-handler` and `load-config` name `error-handler` as their error workflow: `load-config` names none, since `error-handler` calls it, and naming the handler there would loop the two into each other.

| Workflow | Started by | What it does |
|---|---|---|
| `gmail-entry` | The Gmail Trigger, every minute | Polls for labeled PDF mail and passes the whole poll to `intake-email` in one call |
| `intake-email` | `gmail-entry`, or the dev harness | Loads and checks the config, splits each email into one item per attachment, keeps the PDFs, records each one once, and calls `process-invoice` once per new attachment |
| `process-invoice` | `intake-email`, or the dev harness | Screens the PDF, calls `extract-invoice` with up to one retry, saves the record, files the PDF in Drive, writes the Sheets rows, labels the email, and records the outcome |
| `extract-invoice` | `process-invoice`, or the dev harness | Sends the text to the Information Extractor or the PDF to the Messages API, then checks the reply and returns one verdict |
| `ensure-folder` | `process-invoice` | Finds or creates a Drive folder by exact name under a parent and returns its ID |
| `load-config` | `intake-email`, `daily-summary`, `error-handler`, and the dev harness | Reads `/files/config/config.json` into `{ config }` |
| `daily-summary` | A schedule at 18:00 Bogota time, or the dev harness | Emails the team an HTML report of the last 24 hours; a dev-harness call gets the rendered report back and sends nothing unless it passes `dry_run: false` |
| `error-handler` | Any other workflow’s failure | Emails the team a plain-text alert with the workflow, node, error, execution link, and time |
| `dev-harness` | `POST /webhook/dev` with `X-Dev-Token` | Runs one of five targets: `load-config`, `extract-invoice`, `process-invoice`, `intake-email`, or `summary-preview` |

Inside those workflows, five Code nodes do work that no native node does: `Check config`, `Check invoice`, `Build PDF request`, `Prepare record`, and `Render summary`. Each one is a pure TypeScript function in `src/nodes/`, which `npm run build:workflows` compiles into the workflow JSON. The same build copies in the SQL from `db/queries/`, the extraction prompt, and the invoice JSON Schema.

The workflows read their instance values from `config/config.json`, mounted read-only at `/files/config/`. It sets the team email, the three Gmail label IDs, the Drive folder and spreadsheet IDs, and the tab names. It also sets the models and effort, the extraction limits, and the review thresholds. Git ignores it, and `config/config.example.json` is its template.

## How an invoice moves from Gmail to its label

The sequence diagram groups the path into seven bands, and the numbered steps below follow the same order:

![Invoice lifecycle: poll, idempotency gate, screens and extraction, Sonnet retry, replay-safe save, duplicate branch, then Drive, Sheets, label, and outcome](diagrams/invoice-sequence.svg)

1. **Poll**: Once a minute, the Gmail Trigger in `gmail-entry` searches for `label:invoices has:attachment filename:pdf -label:processed -label:review -label:duplicate`, read or unread. It sees only mail that arrived after its last poll, and it fetches at most 10 emails per poll, leaving the rest for later polls. `Hand to intake` passes the whole poll to `intake-email` in one call, with no field mapping, because that workflow accepts all data.
2. **Idempotency gate**: `intake-email` loads `config.json` and checks it before anything else. It splits each email into one item per attachment and keeps the PDFs, by MIME type or a `.pdf` name in any letter case. `Record event` then inserts each attachment’s event, `<message id>:<attachment key>`, into `processed_events` with `ON CONFLICT DO NOTHING`. A known event comes back as a bare `{success: true}` item with no `event_id`, which `Keep new attachments` drops, so `process-invoice` runs once for each new attachment only.
3. **Screens, extraction, and check**: `process-invoice` reads the PDF’s text layer locally, up to `max_pages` pages. An encrypted or corrupt PDF becomes a review record with reason `unreadable_pdf`, a PDF over `max_pages` (20 by default) gets `too_many_pages`, and neither reaches the model. Any other PDF takes the text path when it has at least `min_text_chars_per_page` (100 by default) non-whitespace characters per page, and the PDF path otherwise. `extract-invoice` calls the default model, Claude Haiku 5.5, at effort `low`. `Check invoice` then turns the reply into one verdict: `ok`, or `review` with reasons such as missing fields, invalid or out-of-order dates, totals off by more than `totals_tolerance`, or confidence below `min_confidence`.
4. **Sonnet retry**: When the verdict is `review` and `ai.retry_model` isn’t empty, `extract-invoice` runs once more with Claude Sonnet 5.5 on the same path. The second verdict is final.
5. **Save**: One SQL statement saves the invoice and its line items once per event. A replay of the same event returns the row from the first save. A different event with the same supplier tax ID and invoice number saves nothing and comes back as a duplicate of the first. Normalization turns `901.384.552-2` and `NIT 901384552 - 2` into one tax ID and `BE-2041` and ` be-2041 ` into one number, and a row without either value never matches.
6. **Duplicate**: A duplicate gets the `Duplicate` label and the `duplicate` outcome, linked to the original invoice, and stops there, with no Drive file and no Sheets rows.
7. **Drive, Sheets, label, and outcome**: `ensure-folder` finds or creates the year and month folders under the Drive root, and `Upload PDF` stores the file as `<date>_<supplier>_<number>.pdf`. `Save Drive link` writes the file ID and URL onto the saved row and reads that row back with its items. The Sheets rows, keyed by `invoice_id` and `item_key`, and the `Processed` or `Review` label all come from that row. The last node records the event’s outcome, which stays NULL until then.

Once a day, at 18:00 Bogota time, `daily-summary` reports the 24 hours that end at the run’s own timestamp, under the run’s Bogota date. An invoice that arrives at 19:00 therefore appears in the next day’s report. The counts come from `processed_events`, while the totals and the review list come only from finished invoices, so totals and counts cover the same invoices. “Due in the next 7 days” lists every saved invoice due from the report day through day +7, finished or not.

## What the pipeline stores, and for how long

Postgres is the system of record, and the Drive files, Sheets rows, and Gmail labels all follow from what it saved:

| Store | What it holds | How long |
|---|---|---|
| Table `processed_events` in database `app` | One row per Gmail attachment event: key `(source, event_id)`, `file_name`, `received_at`, `outcome` (`ok`, `review`, `duplicate`, or NULL while unfinished), and `invoice_id` | Until someone deletes it; no job prunes it |
| Table `invoices` in database `app` | One row per saved invoice: `source_event_id` (unique), `status`, `review_reasons`, the normalized fields, `confidence`, `extraction_path`, `model`, `attempts`, the raw reply, and the Drive file name, folder, ID, and URL; unique on `(supplier_tax_id, invoice_number)` and indexed on `received_at` and `due_date` | Until someone deletes it |
| Table `invoice_items` in database `app` | One row per line item, keyed by `(invoice_id, line_no)`; deleting an invoice deletes its items | Until someone deletes its invoice |
| Database `n8n`, plus volume `n8n_data` | n8n’s workflows, its credentials (encrypted with `N8N_ENCRYPTION_KEY`), and its executions, including email bodies and the PDF path’s base64 copies. The PDF binaries sit on the volume in regular mode and in the database in queue mode. | Executions: 168 hours |
| Google Drive | The original PDFs under `<root>/<yyyy>/<mm>/`, dated by the printed issue date, or by the arrival date in Bogota when the issue date isn’t valid | Until staff delete them |
| Google Sheets | Tab `Invoices`, one row per invoice keyed by `invoice_id`, and tab `Items`, one row per line keyed by `item_key` (`<invoice_id>-<line_no>`) | Until staff delete them |
| Gmail | The source emails, each with a `Processed`, `Review`, or `Duplicate` label | Until staff delete them |

## Failure modes: behavior, detection, and recovery

For each failure, the table gives the pipeline’s behavior, the signal you’d notice, and the fix. Unless a row says otherwise, every Gmail, Drive, Sheets, HTTP Request, Postgres, and Information Extractor call makes 3 tries, 1000 ms apart. An Execute Workflow call never retries, since a retry would repeat a sub-workflow’s side effects. A retry from n8n’s executions list resumes at the failed node and reuses the stored output of every node before it, and [Recovering stuck events](../AGENTS.md#recovering-stuck-events) in `AGENTS.md` has the commands.

| Failure | Behavior | Detection | Recovery |
|---|---|---|---|
| Gmail is down or rate-limits the account | A failed poll records a failed `gmail-entry` execution and runs `error-handler`, whose email fails too. The trigger doesn’t advance, so mail waits in Gmail. After 10 failed fetches of one message, the trigger skips it and logs only a warning. A label call that fails stops `process-invoice` after the save. | Only n8n’s executions list: failed `gmail-entry` and `error-handler` runs. A skipped message shows only in n8n’s log. | Polling catches up once Gmail answers. Forward a skipped email again, and retry each failed `process-invoice` execution, which resumes at the label. |
| Anthropic is down, overloaded, or rate-limits the account | The extraction call fails after its retries, so `extract-invoice` and `process-invoice` fail before the save: no `invoices` row, and the outcome stays NULL. | Error emails, and the summary’s unfinished count | Retry the failed `process-invoice` execution once the API answers; it resumes at the extraction call. |
| Claude refuses | On the PDF path, `stop_reason: refusal` becomes the review reason `model_refused`, so the Sonnet retry runs, and a second refusal saves the invoice for review. The text path has no refusal signal: the Information Extractor either parses a reply or fails as in the parse-failure row. | The `Review` label, and the summary’s review list | A person reads the PDF. |
| A reply doesn’t parse or fails a check | On the PDF path, an unparseable reply, or one cut off by `max_tokens` or the context window, becomes a review reason. So do missing fields, invalid or out-of-order dates, a totals mismatch, and low confidence on either path. The Sonnet retry runs once, and a second `review` verdict saves the invoice with its reasons. | The `Review` label, the summary’s review list, and the `status` and `review_reasons` columns in Sheets | A person checks the PDF from the summary’s link. |
| The Information Extractor can’t parse a reply into the schema | Its output parser makes one repair call and then throws, and the node makes 3 tries, so one attempt makes up to 6 model calls. `extract-invoice` and `process-invoice` then fail, with no review fallback and no `invoices` row. | Error emails, and the summary’s unfinished count | A retry alone repeats the failure. Correct the prompt or schema, run `npm run build:workflows` and `npm run setup`, then retry the failed `process-invoice` execution. |
| Gmail delivers the same email twice | The gate keys on `<message id>:<attachment key>`, so the repeat’s insert does nothing. The Postgres node returns a bare `{success: true}` item instead of zero rows, and `Keep new attachments` drops it. | None needed | None needed |
| The `Record event` response is lost | The insert committed, but n8n never saw the response, so the node’s retry finds the row and the event looks known. `process-invoice` never runs, and no error email goes out. | The summary’s unfinished count, 30 minutes after arrival | Delete the event’s `processed_events` row, then forward the email to the inbox again. |
| A supplier re-sends an invoice in a new email | The save finds the supplier tax ID and invoice number and returns `duplicate_of`. The email gets the `Duplicate` label and outcome `duplicate`, with no Drive file or Sheets rows. The extraction runs, and costs tokens, before the duplicate shows. | The `Duplicate` label, and the summary’s duplicate count | None needed |
| Two copies save at the same moment, likeliest in queue mode | The unique index lets one insert win, but the other statement’s snapshot can miss that row, so `duplicate_of` comes back NULL. The copy still gets the `Duplicate` label and outcome `duplicate`, with a NULL `invoice_id`. | `processed_events` rows with outcome `duplicate` and no `invoice_id` | Link the row by hand when it matters. Upgrade: read the original back in a second statement. |
| n8n restarts mid-execution | n8n doesn’t resume an execution that was running: it marks it crashed, and the event’s outcome stays NULL. | The crashed execution, and the summary’s unfinished count | Delete the event’s `processed_events` row, and its `invoices` row if the run reached the save, then forward the email again. Remove any Drive file or Sheets row the run left behind. |
| Calling a workflow right after n8n restarts | `/healthz` reports healthy before the publication reconciler syncs the published versions, every 10s by default, so an early call can run the previous version. `npm run setup` waits 15s after its own restart. | The execution shows the previous version’s nodes | After any other restart, wait 15s past `/healthz` before calling a workflow. |
| Postgres is down | If database `app` fails, `Record event` fails after its retries, and `intake-email` stops before it records anything. A failure later in `process-invoice` stops it at that node. If the whole server is down, n8n can’t run executions either, because its own database is on that server. | The `error-handler` email, and `docker compose ps` showing `postgres` unhealthy | Restore Postgres, then retry the failed executions. The save is replay-safe, so a retry can’t write a second row. |
| Google Drive is down | `ensure-folder` or `Upload PDF` fails after its retries, after the save, so the invoice row exists with outcome NULL. If an upload created the file before it failed, the retry uploads a second copy, and the saved link points at that copy. | Error emails, the summary’s unfinished count, and two Drive files with one name | Retry the failed `process-invoice` execution. Upgrade: look the file up by name first, or skip the upload when the row already has a `drive_file_id`. |
| Two first uploads in a month race | Both can find no `mm` folder and create one, which leaves two month folders with the same name. | Two folders named `mm` under one year | Move the files into one folder. Upgrade: keep folder IDs in Postgres with `INSERT … ON CONFLICT`. |
| Google Sheets is down | A Sheets write fails after its retries, after the save and the upload, and the outcome stays NULL. | Error emails, and the summary’s unfinished count | Retry the failed `process-invoice` execution. Both tabs write by key, so a retry updates rows instead of adding them. |
| `config.json` is missing or isn’t JSON | `Read config file` has Always Output Data on, so `Parse config` throws instead of stopping silently, and `intake-email` fails before it records anything, firing its own caller’s error workflow. `daily-summary` fails too. `load-config` names no error workflow of its own, so `error-handler`’s own call into it fails once and stops instead of looping: `error-handler` can’t email, because it loads the same file, but that single failure doesn’t retrigger itself. | Only n8n’s executions list | Fix the file; n8n reads it on every run, so you don’t need to restart anything. Then forward the affected emails again, since `intake-email` recorded no events. |
| `config.json` has a bad value | `Check config` throws an error naming the first bad key, and `intake-email` fails before it records anything. `error-handler` doesn’t check the config, so its email still goes out unless `team_email` is the bad value. | The `error-handler` email | Fix the value, then forward the affected emails again. |
| A Gmail label ID is wrong | The label call fails after its retries, after the save, the upload, and the Sheets rows, and the outcome stays NULL. | The `error-handler` email | Fix the ID in `config.json`. A retry reuses the config its run started with, so add the label by hand and record the outcome in SQL. |
| A PDF is encrypted or corrupt | `Extract text` takes its error output, and `process-invoice` saves the invoice for review as `unreadable_pdf`, with no AI call. It still files, lists, and labels the invoice `Review`. | The `Review` label with reason `unreadable_pdf` | A person reads the PDF, or asks the supplier for a readable copy. |
| A PDF has more pages than `max_pages` | `process-invoice` saves the invoice for review as `too_many_pages`, with no AI call, then files, lists, and labels it `Review`. | The `Review` label with reason `too_many_pages` | A person reads the PDF, or raises `max_pages` in `config.json`. |
| A scanned PDF has a poor text layer | Text density is the only routing signal. A text layer with at least `min_text_chars_per_page` non-whitespace characters per page takes the text path even when its text is wrong, and the Sonnet retry stays on that path. The checks flag a totals mismatch or low confidence, but consistently wrong values can pass. | The `Review` label, when a check fails | A person reads the PDF. Upgrade: retry a text-path review on the PDF path. |
| One failure sends two or more alerts | n8n runs the error workflow for each failed execution in a chain, so a failure inside `process-invoice` alerts from it and again from `intake-email`, its caller. | Two or more emails for one chain of executions | None needed; count incidents by execution, not by email. |
| n8n misses the 18:00 run | The schedule skips a run that n8n missed, and the next report covers only its own 24 hours, so the missed run’s 24 hours never appear in a report. | No summary email that day | Send it through the dev harness’s `summary-preview` target, with `run_at` set to the missed 18:00 and `dry_run: false`. |

## Where the default stack stops scaling

The default stack is one n8n process and one Postgres server. Each limit below names the ceiling it sets and the change that lifts it:

- **One n8n process**: `compose.queue.yaml` adds Redis and `n8n-worker` containers, and each worker runs up to 10 executions at once, n8n’s default. In queue mode, n8n 2.45.6 stores binary data in the database instead of on the main process’s disk, so a worker can read a PDF that the main process received. A test run of `intake-email` through the dev harness on the queue stack confirmed it: the execution ran on a worker and read the PDF, then failed only on the missing Anthropic credential. The override gives Redis no password and no volume, so set `QUEUE_BULL_REDIS_PASSWORD` before production use.
- **Gmail polling**: The trigger polls once a minute and fetches at most 10 emails per poll, keeping the rest pending for later polls. A burst of 50 emails therefore takes about 5 minutes to enter. Gmail meters API calls in quota units per user and per project per minute ([Gmail API usage limits](https://developers.google.com/workspace/gmail/api/reference/quota)), and every call here runs as the one demo account.
- **Anthropic**: The API limits each organization per model class, in requests, input tokens, and output tokens per minute, and the limits rise with the usage tier ([Anthropic rate limits](https://platform.claude.com/docs/en/api/rate-limits)). At the Start tier, Claude Haiku 5.5 allows 4,000 requests per minute. Each extraction attempt makes one call when it succeeds; failures raise that to 3 tries on the PDF path, or 6 calls on the text path with its repair calls. Past a limit, the API answers 429, and the node-level retries, a fixed 1000 ms apart, don’t outlast a per-minute limit, so the invoice waits for a manual retry.
- **Google Sheets**: The API allows 60 write requests and 60 read requests per minute per user per project ([Sheets API usage limits](https://developers.google.com/workspace/sheets/api/limits)). Each invoice makes 4 reads, 2 per tab: one finds the tab by name, and one reads its rows. With up to 4 writes per invoice as well, the one account tops out near 15 invoices a minute. Upgrade: batch the rows, or export the sheet from Postgres on a schedule.
- **PDF copies in execution data**: On the PDF path, the PDF’s base64 text sits in the output of `Encode PDF`, `Request settings`, and `Build PDF request`, and n8n keeps execution data for 168 hours. A PDF can be up to about 95 MB, so one attempt can add about 380 MB. Upgrade: upload each PDF once with the [Files API](https://platform.claude.com/docs/en/build-with-claude/files) and send its `file_id`; uploaded files stay until deleted, so delete each one after its extraction.
- **Request size**: `Build PDF request` refuses a PDF over about 95.3 MB before the call. Its base64 must fit the first-party API’s 128 MB request limit, less 1 MB for the rest of the body ([PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support)). Gmail’s 25 MB attachment limit ([Gmail help](https://support.google.com/mail/answer/6584)) keeps most emailed PDFs far below that, so the guard rarely binds. Other deployments accept less ([request size limits](https://platform.claude.com/docs/en/api/overview#request-size-limits)): 32 MB on Claude Platform on AWS, Google Cloud (Anthropic managed), and Microsoft Foundry, 30 MB on Google Cloud (Google managed), and 20 MB on Amazon Bedrock.
- **Postgres**: The summary query joins every finished invoice before it filters by date, so its cost grows with history. Add a date filter and an index on `processed_events.invoice_id` as the tables grow, since no job prunes them.

## Security: untrusted documents, secrets, and retention

The pipeline treats every invoice as untrusted input: the model’s output is only ever data, and each value is bound, escaped, or written raw before it reaches SQL, HTML, or Sheets. Each control in detail:

- **Prompt injection from a document**: The prompt tells the model to treat everything in the document as data, including text that reads like an instruction. The output is data only, through structured output on the PDF path and the extractor’s schema on the text path, with no tools to call. Planted values that break the totals, date, or confidence checks land in review. A self-consistent planted set passes as `ok`, though, and the model reports its own confidence, so check the PDF, not the Sheets row, before paying. Sheets writes use `RAW`, so a value like `=IMPORTXML(…)` stays text.
- **HTML and email**: The daily summary HTML-escapes every value from the database, URLs included, and links a PDF only when its Drive URL starts with `https://`. Error emails are plain text, with no n8n attribution.
- **SQL**: Every query passes values as `$n` parameters, and `npm run check` rejects a query built from an expression. n8n formats those `$n` placeholders on the client before sending the query, replacing every one it finds in the text, so a query's own comments never carry a `$` followed by a digit either — `npm run check` rejects a query that does. The n8n role owns database `n8n` and the app role owns `app`, each with `REVOKE ALL … FROM PUBLIC`, and the Postgres superuser only bootstraps them. `openTestDb` refuses any database not named `postgres`, so a wrong `TEST_DATABASE_URL` can’t drop a real schema.
- **Drive search**: `ensure-folder` builds its Drive query from the folder name and parent ID without escaping quotes. That’s safe only because every caller passes a year, a month, or a Drive ID.
- **Secrets**: Secrets live only in `.env`, which git ignores, and in n8n credentials, encrypted with `N8N_ENCRYPTION_KEY`. n8n also writes that key to its settings file on the `n8n_data` volume, so the volume and database `n8n` together decrypt every credential. `npm run setup` never overwrites an existing Google OAuth2 credential unless it runs with `--force`, no script prints credential data, and continuous integration (CI) runs gitleaks over the full history.
- **OAuth scopes**: The three Google credentials keep n8n 2.45.6’s default scopes, which reach further than this pipeline needs. Gmail’s are `https://mail.google.com/`, `gmail.modify`, `gmail.compose`, `gmail.labels`, and two add-on scopes; Drive’s are `drive`, `drive.appdata`, and `drive.photos.readonly`; Sheets’ are `spreadsheets`, `drive.file`, and `drive.metadata`. In plain terms, `https://mail.google.com/` is full mailbox access, including permanent deletion, and `drive` reaches every file in the account. Narrowing them through each credential’s custom scopes is a production step that needs its own live test.
- **Retention**: n8n prunes executions after 168 hours, including email bodies, PDF binaries, and the base64 copies on the PDF path. Postgres, Drive, and Sheets keep invoices until someone deletes them.
- **Dev harness**: `POST /webhook/dev` needs the `X-Dev-Token` header, and a test pins that gate. Compose publishes n8n’s port on `127.0.0.1` only, with no tunnel. Unpublish the harness before production use.
- **File access**: n8n’s file nodes can read only `/files` (`N8N_RESTRICT_FILE_ACCESS_TO`), where Compose mounts `config/` read-only.

## n8n 2.45.6 behaviors this design depends on

The n8n 2.45.6 source confirms each behavior below, and a stored execution confirms all but the last:

- Set 3.4 and later drops binary data when “include other fields” is off, and this repo’s Set nodes are 3.5. `Describe attachment` keeps the PDF by turning it on with `include: selected` and an empty field list.
- Convert to File replaces `$json` with `{}`, so later nodes read earlier fields through `$('<node>')`.
- A child workflow that accepts all data receives the caller’s whole item, so the caller maps no fields.
- Read/Write Files’ `read` operation builds a fresh item, so `load-config` returns exactly `{ config }`, and its callers merge it back onto their own items.
- An execution started by a webhook or a trigger calls only published sub-workflows; only manual and chat runs call drafts.
- Postgres nodes need typeVersion 2.8 or later for free-text parameters, because earlier versions split a text value on commas.
- Google Sheets 4.7 finds a tab by name only in `name` mode, while `id` mode parses the value as a numeric sheet ID.
- A retry from the executions list reuses the stored output of every node that succeeded, including the config passed down, and resumes at the failed node.
- A sub-execution runs its own `errorWorkflow` on failure, same as a top-level run (`execution-lifecycle-hooks.ts`, mode `integrated`). Its only loop guard is a workflow that names itself as its own error workflow, which is why `load-config` names none: `error-handler` calls it, and naming the handler there would have the two retrigger each other for as long as the failure persists.

## Design decisions, each over its alternative

Each entry names a choice and the option it beat, then gives the reason:

- **Claude Haiku 5.5 at effort `low` on both paths, over a larger default model**: Only a `review` verdict calls Claude Sonnet 5.5, once, on the same path, because Sonnet 5.5 costs 20 times as much per token below 100,000 prompt tokens ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). `npm run scenarios` and `npm run cost` measure accuracy and cost per invoice in the integration pass.
- **Routing by text density, over always sending the PDF**: A PDF with a usable text layer reaches the model as text and costs only text tokens. The PDF path bills every page as extracted text plus a page image ([PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support)). Scanned and image-only PDFs still take the PDF path. The cost is the poor-text-layer case in the failure table.
- **HTTP Request over the native Anthropic node for PDFs**: Only the HTTP Request sends the document block with structured output (`output_config.format`), adaptive thinking, and the configured effort, and it sets `media_type` itself, so an `application/octet-stream` PDF still works. If it fails the live check for a reason that isn’t transient, the fallback is the native node with the schema in its system message, at the model’s default effort.
- **The Information Extractor with the Anthropic Chat Model on the text path, over a second HTTP Request**: The extractor takes any chat-model sub-node, so changing providers means swapping one node. The trade-off is that a reply it can’t parse fails the execution instead of becoming a `review` row, and recovery is manual.
- **Postgres as the system of record, over Sheets**: One statement saves an invoice once per event: a replay returns the first row, and the unique `(supplier_tax_id, invoice_number)` turns a re-sent invoice into a duplicate instead of a second row. The Sheets rows and the label read the saved row back, so a replayed run can’t write values that differ from it.
- **An idempotency gate in the database, over checking first**: One `INSERT … ON CONFLICT DO NOTHING` on the key `(source, event_id)` checks and records in a single step. Two runs with the same attachment can’t both pass, which a `SELECT` before an `INSERT` would allow. The cost is the lost-response case in the failure table.
- **Code nodes, SQL, prompt, and schema built from source, over editing workflow JSON**: Each Code node is a pure, tested TypeScript function, and `npm run build:workflows` writes it, the SQL, the prompt, and the invoice schema into the workflow JSON. CI fails when the committed JSON is stale, and `npm run check` rejects a Code node or query that `scripts/manifest.ts` doesn’t list.
- **Label IDs in config, over looking labels up by name at run time**: The three label IDs come from `config.json`, like the Drive folder and spreadsheet IDs and the tab names. A run makes no lookup calls, and a renamed label still works. `Check config` rejects an empty value before anything runs. The cost is one setup step: reading the label IDs from a temporary Gmail node.
- **Config loaded once per poll and passed down, over each sub-workflow loading its own**: `intake-email` loads and checks the config, and every invoice in that poll uses the same checked copy. The cost is that a retry reuses the config its run started with, so a config fix doesn’t reach a failed run.
- **A thin `gmail-entry` in front of `intake-email`, over one workflow**: `npm run setup` skips publishing `gmail-entry` until the Gmail credential exists, and a run started by the dev harness’s webhook can call only published workflows. With the chain in `intake-email`, behind a trigger that needs no credential, the harness runs all of it without Gmail.
- **A rolling 24-hour summary window, over the calendar day**: An 18:00 report on the calendar day would miss everything that arrives after 18:00. The window ends at the run’s own timestamp, under the run’s Bogota date, so each arrival appears in exactly one report, unless n8n misses a run.
