# Test suites

This page lists every test suite in the repo: its command, what it covers, and how it stays deterministic and clean. It ends with what continuous integration (CI) actually runs and the live checks that stay outside every suite.

## Unit and tooling (Vitest)

**Command:** `pnpm test` (`vitest run`, config `vitest.config.ts`, excludes `tests/db/**`).

Covers every TypeScript module outside `tests/db/`:

- `tests/lib/*.test.ts`: the pure invoice logic: `parse-reply` (reading a model reply into a candidate invoice), `normalize-invoice` (dates, amounts, and tax IDs into one comparable shape), `validate-invoice` (the review-reason rules: missing fields, bad dates, a totals mismatch, a supplier that is the buyer's own tax ID, low confidence), `util`, `file-name` (the Drive file name and `<yyyy>/<mm>` folder), `config` (`checkConfig`, including `team_locale` and the `REPLACE_ME` placeholder at any key, starting from `tests/fixtures/config.ts`'s `filledConfig()`), `format` (`escapeHtml` and the locale-aware `formatMoney`), and `strings` (every `SUMMARY_STRINGS`/`ERROR_ALERT_STRINGS` entry present and non-empty in both `en` and `es`, every review reason labeled in both languages by `REASON_LABELS`, an unknown reason falling back to its code, and `STATUS_LABELS` matching the Gmail label words). `tests/lib/retry-policy.test.ts` pins which review reasons earn the Sonnet retry. `tests/lib/contract.test.ts` checks `schemas/invoice.schema.json` and `prompts/extract-invoice.md` against `src/lib/invoice.ts`'s own field list, that the prompt contains none of `{`, `}`, `@`, or a run of 10 or more digits, and that the schema holds every per-field rule (date format, ISO 4217 currency, label-free tax ID and invoice number, combined tax, line order, confidence range) while the prompt states none of them.
- `tests/nodes/*.test.ts`: the nine Code-node sources, each run through `tests/helpers/run-generated.ts` (which executes a node's compiled `jsCode` as n8n's sandbox does, with `$input` and the ambient `DateTime` in scope; `runGeneratedItem` runs a per-item node on one whole item as `$input.item`): `check-config`, `check-invoice`, `build-pdf-request` (including the request-size guard before the call), `prepare-record`, `render-summary` (including the unfinished-event list, its cap at 20, the byte-identical empty day, reasons in words, the two-column review and due lists with no `<style>`, media query or overflow wrapper, and a `$` in an invoice number reaching the link text unchanged), `error-alert` (both of the last two across `en` and `es`, since they share `src/lib/strings.ts`'s message tables), `check-approval` and `approval-note` (a reviewer's corrected row normalized and approved or refused with a note, in both languages: an invalid date, a total at or below zero, the buyer's NIT or a future date is a note, never an approval), and `mark-as-pdf` (an octet-stream attachment relabeled as `application/pdf` with its data reference and other binaries untouched, and any other type passing through unchanged, on both the source and the generated `jsCode`).
- `tests/workflows/*.test.ts`: every committed workflow file's pinned nodes, wiring, and settings, read through `tests/helpers/workflow-file.ts`'s `workflowFile`/`nodeOf`/`sourcesOf`. Workflow expressions get behavioral tests through `tests/helpers/expression.ts`, which evaluates an n8n `={{ }}` parameter in a plain V8 context with `$json`, `$('Node').first().json`, and `$input.all()` stubbed, so `Is duplicate conflicting?` (a matching, a differing, and a missing original), `Look up the original`'s and `Record duplicate`'s parameters, the text-or-vision path, and `Fail the batch`'s message are each run, not just string-matched: `platform.test.ts` (no workflow saves manual executions, since most carry Gmail content or an invoice's extracted fields, and no sticky note sits over a node), `gmail-entry.test.ts`, `intake-email.test.ts` (including `Mark as PDF` and `Fail the batch`), `process-invoice.test.ts` (including a racing duplicate and the text-path threshold), `extract-invoice.test.ts` (the text/PDF routing and the review-reason contract), `dev-harness.test.ts` (including the `process-invoice` target's config check and the `ensure-folder` target), `ensure-folder.test.ts` (the Drive search's escaping of `\` and `'`), `approve-invoices.test.ts` (the 5-minute poll, the review-only read, the blank-name filter, the one-call-per-row batch), `approve-invoice.test.ts` (save, then sheet row with the saved values, then the labels unless another attachment still needs review; the built `Check approval` and `Render approval note` code run too; `already_approved` treated as approved; a refusal written to the row; nothing touches Drive or sends mail), `daily-summary.test.ts`, and `error-handler.test.ts` (both of the last two covering `team_locale`'s wiring). A hand edit to `workflows/*.json` that drifts from the generated or reviewed form fails here before it fails anywhere live.
- `tests/summary-window.test.ts`: the daily summary's 30-minute stuck window and 20-row list cap are stated once, in `db/queries/daily-summary.sql`, quoted the same way in `docs/architecture.md` and `docs/database.md`, and absent from `src/nodes/render-summary.ts`.
- `tests/tooling.test.ts`, the workflow build and hygiene tools (and which workflows `setup` holds back until a credential exists, `approve-invoices` among them), against `tests/fixtures/workflows/` (`clean.json` plus one defect per other fixture: `bad-credential.json`, `leaky.json`, `no-why.json`, `pinned.json`, `volatile.json`) and the fixture Code-node source `tests/fixtures/nodes/double-value.ts` plus the fixture generated-text sources `tests/fixtures/text/read-rows.sql` and `tests/fixtures/text/system.md`, so a build or hygiene test never depends on a real `src/nodes/*.ts` or `db/queries/*.sql` file changing underneath it. It also covers the per-item wrapper (`perItem: true` returns `run($input.item)`) and the build's refusal of a `perItem` entry on a node that doesn't run once for each item. The build writes each Code node's `Why Code:` note from its manifest reason, and `check` rejects a Code node without one.
- `tests/release-workflow.test.ts`: `.github/workflows/release.yml` runs its release job only for a merge from `develop` or a `release/*` branch, and `SECURITY.md` names only the services this repo uses and has a supported-versions section.
- `tests/readme.test.ts`: `README.md`'s shape: its `## ` sections in the repo standard's order, the architecture image before "What it does", a quick start of at most five commands, and a `### Live checks` table of at least 25 rows covering setup, the pipeline, the drills, queue mode, and a clean clone, a quick start that names its prerequisites, no live-check cell over 200 characters, and no bare bold label line.
- `tests/docs.test.ts`: the documentation set. `AGENTS.md` stays under 160 lines and 14,000 bytes, every relative link in it resolves, no document uses a spaced em dash as punctuation, and (once the diagrams exist) every diagram is referenced from the README, `docs/architecture.md`, and `docs/diagrams/README.md`.
- `tests/hygiene.test.ts`: scans every tracked and untracked (but not git-ignored) file for a reference to a plan task, a brief, or a ruling instead of the file stating its own reason; `pnpm-lock.yaml` and the test file itself are exempt.
- `tests/supply-chain.test.ts`: reads `pnpm config list --json` (pnpm's effective config, not the raw YAML) to check `pnpm-workspace.yaml`'s settings (`minimumReleaseAge`, the empty `minimumReleaseAgeExclude`, `trustPolicy`, `blockExoticSubdeps`, `strictDepBuilds`, `engineStrict`, `allowBuilds`), `packageManager`'s exact pnpm-11 shape, that `package-lock.json` doesn't exist, that no tracked file still teaches an `npm` command, that every Compose `image:` line carries a `@sha256:` digest, and that every `docker run` image across `.github/workflows/*.yml` does too, and, through the merged Compose config, that every long-running service runs with `no-new-privileges`, with `n8n` and `n8n-worker` dropping every Linux capability.
- `tests/runtime.test.ts`: `compose.yaml`, `.env.example`, and `config/config.example.json` against each other: the services' wiring, and the config template's keys and shape.
- `tests/runtime-lib.test.ts`: `scripts/lib/runtime.ts`'s `compose()` wrapper and `isWebhookLive`/`waitForWebhookLive`, against a mocked `child_process.spawn`, never a live Compose process.
- `tests/dev-client.test.ts`: `scripts/lib/dev-client.ts`'s `callDev`, with `process.loadEnvFile` stubbed so a developer's own `.env` can't change the outcome.
- `tests/db-migrate.test.ts`: migration ordering, `\getenv` extraction, and the transaction-control and password-logging guards in `scripts/db-migrate.ts`, against `db/migrations/001_runtime_role.sql` directly, no live database.
- `tests/lib/sheet-values.test.ts`: the Sheets serial date and the cell-to-text helpers the approval reads its row with.
- `tests/check-db.test.ts`: the denial/grant/role-fact predicates and the generated psql script in `scripts/check-db.ts`, against static fixtures.
- `tests/samples.test.ts`: the six generated sample invoices: `scripts/lib/invoice-pdf.ts` renders each one and `pdfjs-dist` reads its text layer back, checked against `scripts/lib/sample-invoices.ts`'s own expected fields and the file name `invoiceFileName` would produce; an accented supplier name (`Distribuidora Cañaveral – Café Ñandú`) reads back exactly.
- `tests/scripts/generate-adversarial-samples.test.ts`: every hidden-text adversarial fixture's planted content actually survives the same `pdfjs-dist` text extraction `process-invoice`'s own `Extract text` node performs, so a fixture that looks right on paper can't silently test nothing.
- `tests/scripts/check-scenarios.test.ts`: `scripts/check-scenarios.ts`'s pure `compareScenario`, `loadExpectedSamples`, and `parseSince`, against `scripts/lib/sample-invoices.ts`'s expectations, no live Postgres.
- `tests/lib/ai-cost.test.ts` and `tests/lib/pricing.test.ts`: the per-call cost estimate (real usage on the PDF path, text length on the text path), the price table, and `hasPrice`.
- `tests/scripts/measure-cost.test.ts`: `scripts/measure-cost.ts`'s `parseArgs`, `summarizeCosts`, and `fetchPage` (an API error keeps n8n's response body, with `fetch` stubbed), against synthetic n8n execution data.
- `tests/scripts/check-dev-response.test.ts`: `scripts/check-dev-response.ts`'s `isSummaryPreview`, against fixed HTML strings, no live webhook.
- `tests/scripts/init-env.test.ts`: `scripts/init-env.ts`'s `fillSecrets`, `writeEnvFile`, and `ensureN8nImportDir`, each against a fresh `mkdtempSync` directory under the OS temp dir, never the repo itself.

**Staying deterministic and clean:** `vitest.config.ts` excludes `tests/db/**` explicitly, so this run never needs a database. `tests/setup.ts` provides the ambient `DateTime` global the Code-node sandbox exposes at runtime, so a Code-node source under test sees the same global shape it would in n8n. No test in this suite opens a network connection; the `mkdtempSync`-based tests above are the exception to "no filesystem access," and none of them write inside the repo.

## Database (Vitest against `testdb`)

**Command:** `TEST_DATABASE_URL=postgres://postgres@127.0.0.1:55432/postgres pnpm run test:db` (`vitest run --config vitest.db.config.ts`, which targets `tests/db/**` with `fileParallelism: false`). Needs the `testdb` Compose service (profile `test`, tmpfs-backed, trust auth, bound to `127.0.0.1:55432`) already running: `docker compose --profile test up -d --wait testdb`.

`tests/db/queries.test.ts` exercises every file in `db/queries/` as `app_runtime`, the way the Postgres node binds parameters, through `tests/db/helpers.ts`'s `openTestDb`: on open, it drops and recreates `schema public` from `db/schema.sql`, then applies every file in `db/migrations/` to it (through `scripts/db-migrate.ts`, pointed at the `testdb` service and its `postgres` database). Covered: recording an event once, saving an invoice and its items, a second event with the same supplier tax ID and invoice number becoming a duplicate (including a conflicting duplicate with a different total or issue date, a genuine re-send whose values compare equal, and a save racing another session's uncommitted save of the same key, which returns no `duplicate_of`, while `find-original.sql` in the next statement finds the committed original), `find-original.sql` returning one all-NULL row when no invoice holds the key, `record-outcome.sql` returning `{ event_id, outcome }` on every call and storing an empty invoice ID as NULL, saving the same event twice returning the first invoice, a review row with no tax ID or number never conflicting, an out-of-range amount and a year-0000 date both saving cleanly as a review row, the Drive-link update reading the row back with ordered items, `openTestDb` refusing a database that isn't literally named `postgres`, the daily summary's half-open 24-hour window (an event exactly 24 hours before the run is included, exactly at the run is excluded, one second before the window start is excluded) the unfinished count and list measured at the run's own `run_at` (oldest first, capped at 20), and its totals, review list, and "due in the next 7 days" section, and the scenario report joining events, invoices, items, and a duplicate's own source file name.

**Staying deterministic and clean:** `openTestDb` refuses to run against any database not literally named `postgres`, so a misconfigured `TEST_DATABASE_URL` can't drop a real schema. `reset()` truncates `invoices`, `invoice_items`, and `processed_events` with identity restart before every test. CI's `db` job runs it against the same `testdb` service on every PR. The racing-save test holds one session's transaction open and waits, through `pg_locks`, until the other is blocked on it, polling `pg_locks` every 50 ms, at most 100 times, never a fixed sleep.

## What CI runs

| CI job | What it runs |
|---|---|
| `quality` | `pnpm install --frozen-lockfile`, `typecheck`, `lint`, `test` (the full Vitest suite above, minus `tests/db/`), `build:workflows -- --check`, `check`, then ShellCheck on every tracked `*.sh` file. |
| `security` | gitleaks in git mode over the full history, `pnpm audit --audit-level=high`. |
| `actions` | actionlint and zizmor against the workflow files themselves. |
| `db` | `pnpm install --frozen-lockfile`, `node scripts/init-env.ts`, `docker compose --profile test up -d --wait testdb`, then `pnpm run test:db` against `TEST_DATABASE_URL=postgres://postgres@127.0.0.1:55432/postgres`, tearing down with `docker compose --profile test down -v` in an `if: always()` step. |
| `n8n` | `pnpm install --frozen-lockfile`, `node scripts/init-env.ts`, `cp config/config.example.json config/config.json`, `docker compose up -d --wait postgres n8n`, `pnpm run setup`, `node scripts/check-db.ts`, `node scripts/check-dev-response.ts`. This is the one job that boots the real stack and proves a workflow executes, both the app Postgres path and a generated Code node, not just that the committed JSON is well-formed. Tears down with `docker compose down -v` in an `if: always()` step, and prints `docker compose logs n8n postgres` on failure. |
| `codeql` | `.github/workflows/codeql.yml`, on every pull request, every push to `main` and `develop`, and weekly: CodeQL's `javascript-typescript` and `actions` analyses (`docs/diagrams/` excluded). It skips a private fork or copy, where CodeQL needs a paid license. |

**What CI doesn't run, and why:** `pnpm run scenarios` (needs a real Anthropic credential CI doesn't have) and `pnpm run cost` (a report over the n8n API's own execution history, not a check: there's nothing for CI to assert) both stay manual. The queue-mode stack (`compose.queue.yaml`) adds nothing `check-dev-response.ts` doesn't already prove about Code-node and Postgres execution, so it's verified once by hand and recorded in `docs/architecture.md`'s scaling section, not re-run on every PR.

## Coverage

**Command:** `pnpm run test:coverage` (`vitest run --coverage`, V8 provider, `src/` and `scripts/`). There is no threshold; run it when you add a module. The report prints to the terminal (text reporters only); V8 uses `coverage/` as scratch space while it runs, and git ignores it.

The `src/` logic sits above 90% statements. These `scripts/` files are mostly or wholly outside the unit tests, because they drive a running stack or write files. Each line says what covers it instead:

- `scripts/dev-call.ts` is at 0% statements. `node scripts/check-dev-response.ts` and the harness drills call the same endpoint.
- `scripts/generate-samples.ts` is at 0% statements. Regenerating the samples and checking `git diff` on them covers it.
- `scripts/import-workflows.ts` is at about 19%: only `missingTriggerCredentials` is unit-tested. the stack round trip (`pnpm run setup`) covers the rest.
- `scripts/export-workflows.ts` is at about 30%: only `normalizeWorkflow` is unit-tested. the stack round trip (`pnpm run export`, then `git diff --exit-code workflows/`) covers the rest.

## Deferred live checks

The checks that need the Google and Anthropic accounts, rather than the local stack, are the README's [`### Live checks`](../README.md#live-checks) table: the live model calls behind `pnpm run scenarios` and `pnpm run cost`, the Drive files and Sheets rows, the Gmail labels, the error alerts, the drills, queue mode, the red-team fixtures, and a clean clone. Each row names its exact command, or the manual action where none exists, and its expected result.
