# AGENTS.md

Guidance for anyone — human or AI — working in this repository.

## Purpose

This repo builds an AI invoice-processing pipeline for Magdaport S.A.S., a fictional wholesale distributor in Barranquilla, Colombia, as an n8n workflow backed by Postgres. It is a portfolio demo: every file should read as production-quality, not a prototype.

## Repo map

- `compose.yaml`, `.env.example` — the local runtime: Postgres and n8n in Docker Compose, plus the opt-in `testdb` service (profile `test`) used only by `pnpm run test:db`.
- `compose.queue.yaml` — an optional override that adds Redis and `n8n-worker` containers for queue mode; see Commands.
- `db/schema.sql`, `db/init/` — the application database schema and the one-time role/database bootstrap script. `db/queries/*.sql` — the parameterized queries the workflow's Postgres nodes run verbatim (`$1`, `$2`, ... placeholders only, never string-built SQL), exercised by `tests/db/queries.test.ts` against `testdb`.
- `config/config.example.json` — the config template; a developer's own `config/config.json` is gitignored.
- `scripts/manifest.ts` — the single source of truth for fixed workflow/credential IDs and the `CODE_NODES`/`TEXT_PARAMS` tables; `scripts/lib/` holds the shared workflow and runtime (Docker/`.env`) helpers, the dev-harness client, and the sample-invoice generator (`sample-invoices.ts` for the pinned data and expected results, `invoice-pdf.ts` for rendering and rasterizing them).
- `scripts/check-workflows.ts`, `scripts/build-workflows.ts`, `scripts/export-workflows.ts`, `scripts/import-workflows.ts`, `scripts/setup-credentials.ts`, `scripts/dev-call.ts`, `scripts/generate-samples.ts`, `scripts/check-scenarios.ts`, `scripts/measure-cost.ts` — the workflow tooling, sample-data, and reporting CLIs; see Commands below. `scripts/lib/pricing.ts` holds the per-model USD rates `measure-cost.ts` prices every call against.
- `scripts/sql/scenario-report.sql` — reads `processed_events`, `invoices`, and `invoice_items` into one row per Gmail event, for `check-scenarios.ts` to compare against `samples/expected.json`. Unlike the queries in `db/queries/`, it's read through `psql` directly (see Commands), not the Postgres node, so it isn't addressed by `scripts/manifest.ts`'s `TEXT_PARAMS`.
- `samples/` — the six generated sample invoice PDFs and `expected.json`, the extraction result each one should produce. Regenerated by `pnpm run samples`; see Commands below.
- `schemas/invoice.schema.json`, `prompts/extract-invoice.md` — the invoice extraction contract: the structured-output JSON Schema and the system prompt, both copied verbatim into workflow JSON by `pnpm run build:workflows` via `scripts/manifest.ts`'s `TEXT_PARAMS`.
- `src/nodes/` — one `run()` function per Code node, compiled into workflow JSON by `pnpm run build:workflows`: `check-invoice.ts` (parses a model reply and applies the review rules, used by both extraction paths), `build-pdf-request.ts` (builds the Messages API body for the vision path; throws before the call if the PDF's base64 would push the request past the first-party Messages API's 128 MB limit, about 95.3 MB of PDF), `prepare-record.ts` (turns every extraction outcome — a real check result, or a skip taken before any AI call ran — into one record and builds its Drive file name, used by `process-invoice`), and `check-config.ts` (validates the config `load-config` just returned, used by `intake-email`). `src/lib/` holds the pure logic behind them: the invoice types (`invoice.ts`), `util.ts` (small helpers shared by more than one module: date validity, a plain-object check, a fresh empty invoice), `parse-reply.ts`, `normalize-invoice.ts`, and `validate-invoice.ts` (used by `check-invoice.ts`), `file-name.ts` (the Drive file name and folder, used by `prepare-record.ts`), and `config.ts` (the `Config` type and `checkConfig`, used by `check-config.ts`). `src/globals.d.ts` declares the ambient `DateTime` those sources use.
- `tests/` — Vitest tests; `tests/fixtures/` holds workflow and Code-node fixtures, `tests/helpers/run-generated.ts` runs a generated Code node's output the way n8n's sandbox does, and `tests/helpers/workflow-file.ts` reads a real workflow from `workflows/` and looks up a node or its wired-in sources, used by `tests/workflows/*.test.ts`. `tests/db/helpers.ts` opens the local test database and runs a query file from `db/queries/` the way the Postgres node binds parameters, for `tests/db/queries.test.ts` — run separately from `pnpm test` (see Commands).
- `tsconfig.json`, `eslint.config.ts`, `vitest.config.ts`, `vitest.db.config.ts`, `package.json` — the TypeScript toolchain.
- `workflows/` — the n8n workflow JSON, mounted read-only into n8n and imported by `pnpm run setup`. In place: `load-config` (reads and parses `/files/config/config.json`, failing loudly instead of silently when it's missing; names no error workflow of its own, since `error-handler` calls it and naming the handler here would loop the two into each other — a caller's own failed call still fires the caller's own error workflow), `error-handler` (the shared error workflow: loads config, emails the team a plain-text alert), `ensure-folder` (finds or creates a named Drive folder under a parent, by exact name), `dev-harness` (a token-protected, localhost-only webhook for calling a sub-workflow directly; see Commands), `extract-invoice` (routes on `path` to a text branch — an Information Extractor and its Anthropic Chat Model sub-node — or a PDF branch — an HTTP call to the Messages API — and applies the review rules to whichever reply comes back. Rule failures, and a refusal or truncation on the PDF path, come back as `status: 'review'`; an Information Extractor parse or schema failure fails the execution instead, with no automatic review fallback — see the README's Limitations), `process-invoice` (reads the PDF locally and screens its page count, calls `extract-invoice` with one retry on a stronger model when configured, saves the record once per event, files the PDF in Drive, appends it and its line items to Sheets by key, and labels the source email before marking the event's outcome. Neither call into `extract-invoice` sets an error output, so a failure there fails this execution outright instead of becoming a review row — see the README's Limitations. Its last node can finish with zero output items — for example, when there's nothing to update in `processed_events` — so a caller must not rely on reading a result from it directly; the dev harness sets Always Output Data on its own call for exactly that reason), `intake-email` (the idempotency gate, entered via its own Execute Workflow Trigger — `When called`, accept all data, so it needs no credential and `pnpm run setup` publishes it like any other sub-workflow; also reachable through the dev harness by that same name: config is loaded once per call and checked by the generated `Check config` node before anything else runs; each email item is split into one item per attachment; only PDF attachments survive, by MIME type or a case-insensitive `.pdf` name; each surviving attachment's event is recorded once in `processed_events` — a fresh event's row comes back with its `event_id`, but a known one is suppressed by `ON CONFLICT DO NOTHING`, which the Postgres node reports as a bare `{success: true}` item with no `event_id` instead of as zero rows, since this is an INSERT, not a SELECT; `Keep new attachments` matches on `event_id`, so only the fresh ones reach `process-invoice`, called once per item so one bad PDF fails only its own call. See the README's Limitations for what happens when a `Record event` response is lost), `gmail-entry` (a thin entry point: a Gmail Trigger polls labeled PDF attachments every minute, read or unread, and `Hand to intake` passes the whole poll — every email from it, still as separate items — to `intake-email` in one call, waiting for it to finish; neither node retries, and the handoff sets no error output, so any failure fires the shared error workflow instead of silently repeating `intake-email`'s side effects), and `daily-summary` (two triggers — a Schedule Trigger at 18:00 Bogota, and an Execute Workflow Trigger for the dev harness's `summary-preview` target — each shaped by its own Set node into one `{ run_at, dry_run }` item before `Load config` runs; because `Load config`'s own output carries no caller fields through (see below), a `Merge` node puts that shape back next to `config` before the generated `Render summary` node turns the one summary row into an escaped HTML email, and an `IF` on `dry_run` either returns `{ subject, html }` for a preview or sends it). Fixed ids and file names are in `scripts/manifest.ts`.
- `docs/architecture.md` — the architecture doc: components, the invoice lifecycle, the data model, failure modes with detection and recovery, scaling and security notes, platform behaviors, and design decisions. Update it whenever a change alters any of those.
- `docs/diagrams/` — the system architecture (`architecture.*`) and invoice sequence (`invoice-sequence.*`) diagrams. Each `*.json` file is a diagram's source: archify renders the `*.html` page from it, and the `*.svg` image is that page's own SVG export. Edit only the JSON, then regenerate the other two (see Commands).
- `.n8n-import/` — created locally by `node scripts/init-env.ts`; a scratch directory the export tooling writes to. No credential data crosses it at all: `setup-credentials.ts` streams the decrypted import JSON into the `n8n` container over stdin, and reads back the existing-credentials export (still encrypted — ids, names, types, and encrypted data, of which only the ids are used) over stdout — both travel entirely inside the container's own `/tmp`, never through this bind mount (see that script's own comments on `IMPORT_SCRIPT` and `EXPORT_SCRIPT`). It's a live bind mount: never `rm -rf` it. On Linux, it works only when the host uid matches n8n's container uid (1000), because n8n writes into a directory the host creates at 0700.

## Commands

- `pnpm install --frozen-lockfile` — install dependencies from the lockfile.
- `pnpm run typecheck` — `tsc --noEmit`.
- `pnpm run lint` — `eslint .`.
- `pnpm test` — `vitest run`.
- `pnpm run samples` — regenerates the six sample invoices in `samples/` and the extraction result each one should produce (`samples/expected.json`) from `scripts/lib/sample-invoices.ts`. Add `-- --base-date YYYY-MM-DD` to pin the date the samples are built from; it defaults to today in `America/Bogota`. Run `pnpm run samples -- --base-date <today>` before a demo so the daily summary's "due in the next 7 days" section has entries, and commit the regenerated files whenever the sample data or its PDF layout changes.
- `docker compose up -d --wait` — start Postgres and n8n, and wait for both to report healthy.
- `docker compose down` — stop the stack. Add `-v` to also drop the named volumes (destructive: wipes the database and n8n's data).
- `docker compose up -d --wait testdb` — start the local, opt-in test database (profile `test`, tmpfs-backed, trust auth, bound to `127.0.0.1:55432`) used only by `pnpm run test:db`. It's separate from the `postgres`/`app` runtime databases and never holds real data; naming it explicitly starts it even though its profile isn't active, and the main stack is left alone.
- `docker compose -f compose.yaml -f compose.queue.yaml up -d --wait --scale n8n-worker=2` — switch to queue mode: adds Redis and the given number of `n8n-worker` containers, which run executions instead of the main process. `n8n-worker` extends `compose.yaml`'s own `n8n` service (same encryption key, database settings, and read-only `/files` mounts), with its published port reset so it scales past one replica without a conflict. In queue mode, n8n 2.45.6 stores binary data in the database instead of on the filesystem, with no config needed, so a worker can read a PDF a webhook or poll on the main process received — verified by running `intake-email` through the dev harness against this stack: the execution ran on a worker and read the PDF, reaching the same missing-Anthropic-credential failure this demo's build mode hits everywhere else, not an unreadable-PDF one. This recreates the `n8n` container, so the same publication-reconciler lag described below applies: wait at least 15 s past `/healthz` before a call needs to see the active workflow version.
- `docker compose -f compose.yaml -f compose.queue.yaml down && docker compose up -d --wait` — return to the regular, single-process stack. Plain `down`, with no `-v`, keeps the named volumes.
- `TEST_DATABASE_URL=postgres://postgres@127.0.0.1:55432/postgres pnpm run test:db` — runs `tests/db/**` (currently `tests/db/queries.test.ts`) against that test database: on open, it drops and recreates `schema public` from `db/schema.sql`, then exercises every file in `db/queries/` the way the Postgres node would run it. It refuses to run against any database not literally named `postgres`, so a misconfigured `TEST_DATABASE_URL` can't drop a real schema. Not part of `pnpm test` or its `tests/db/**` exclusion; CI runs it in a separate `db` job against its own Postgres service.
- Changing `db/schema.sql` doesn't retroactively apply to the running dev database: either run `docker compose exec postgres psql -U "$APP_DB_USER" -d app` by hand with the new statements, or reset the `pgdata` volume (`docker compose down -v`, destructive — needs the owner's OK) so `db/init/` reloads the schema from scratch.
- `pnpm run build:workflows` — bundles each `src/nodes/*.ts` Code node with esbuild into its node's `jsCode`, and writes every generated text parameter (SQL queries, the extraction prompt, the invoice JSON Schema) verbatim into the node and parameter that `scripts/manifest.ts`'s `TEXT_PARAMS` names. Add `--check` to fail (exit 1) if the committed JSON doesn't match the source, without writing — that's what CI runs. After an esbuild update, run this and commit the regenerated JSON.
- `pnpm run check` — hygiene checks on every file in `workflows/`: pinned data, a literal email/phone/long id/secret, an unknown credential id, a hand-written or undocumented Code node, a hand-written or undocumented generated query, a missing required setting, an external-service node without retry on fail, and a Postgres query built from an expression instead of `$n` parameters.
- `pnpm run setup` — imports credentials (`scripts/setup-credentials.ts`) then publishes workflows (`scripts/import-workflows.ts`) into the local n8n instance. Skips a credential whose `.env` values are blank, or a Google OAuth2 credential (Gmail, Drive, Sheets) that already exists (pass `--force` to overwrite one deliberately — it carries an interactive Google sign-in that `import:credentials` would otherwise wipe out). Skips a workflow not yet in `workflows/`, and holds back one whose trigger needs a credential that isn't available yet.
- `pnpm run export` — writes n8n's canonical form of every known workflow back to `workflows/` and regenerates their Code nodes and generated text parameters; run this after editing a workflow in the n8n UI, and commit the result.
- `node scripts/dev-call.ts <target> '<json>'` — calls the dev-harness webhook (`POST {N8N_URL}/webhook/dev`) directly, for exercising a sub-workflow without waiting on Gmail's poll. For example, `node scripts/dev-call.ts load-config '{}'`. Localhost only — this demo has no tunnel, and the harness workflow must be unpublished before any production use. An unknown target answers `404 {"error":"unknown_target"}`; a request without the `X-Dev-Token` header is rejected. `load-config`, `extract-invoice`, `process-invoice`, `intake-email`, and `summary-preview` (takes `{ run_at, dry_run }`; with `dry_run: true` it returns `daily-summary`'s rendered `{ subject, html }` without sending) exist today; later work adds more targets the same way.
- n8n's `import:workflow`, `export:workflow`, `import:credentials`, `export:credentials`, and `publish:workflow` CLI commands need no owner account, `--userId`, or `--projectId` (checked against `2.45.6`). `publish:workflow` only takes effect after an n8n restart; `pnpm run setup` restarts n8n itself, but only when it actually published something, then waits for `/healthz`, then 15 s more for the publication reconciler, then polls `dev-harness`'s own webhook (the only published workflow with a `webhookPath` in the manifest) until it stops answering 404 — see "Changing a workflow" below.
- `node scripts/init-env.ts` — writes `.env` from `.env.example`, filling only the names the local stack and the dev harness need a real value for (`POSTGRES_PASSWORD`, `N8N_DB_PASSWORD`, `APP_DB_PASSWORD`, `N8N_ENCRYPTION_KEY`, `DEV_HARNESS_TOKEN`) with random hex, and leaving every other blank value (`N8N_API_KEY`, Anthropic, Google) untouched. Refuses to run if `.env` already exists. The quick start runs this for everyone, not just CI — CI has no repo secrets to fill the file by hand, but a local run gets the same generated local-stack secrets with nothing extra to do.
- `node scripts/check-dev-response.ts` — calls the dev harness's `summary-preview` target with a fixed `run_at` and `dry_run: true`, and asserts the response is exactly `{ subject, html }` with the deterministic subject and HTML structure a fresh, empty CI database renders for that moment (see that script's own comment), exiting 1 (with the mismatched response printed) on a mismatch. The path reaches `Render summary` — the *generated* Code node from `src/nodes/render-summary.ts` — and the app Postgres through `Query summary`, with no third-party credential needed. This is CI's `n8n` job proof that n8n actually executes a generated Code node and a Postgres query, not just that the webhook answers something.
- `pnpm run scenarios -- --since <YYYY-MM-DDTHH:MM:SSZ>` — compares the six sample invoices against `scripts/sql/scenario-report.sql`'s read of real Postgres, run through `docker compose exec -T postgres psql -U "$APP_DB_USER" -d app -At` on stdin, binding `since` with psql's `\bind` meta-command. Prints `| file | result | details |` and exits 1 on any `FAIL`. Rejects a malformed `--since` before building any psql input, since the value lands on a meta-command line. When a file name appears more than once in the report, only its earliest row counts; every extra row is its own `FAIL` detail (`<file>: N extra row`).
- `pnpm run cost -- --since <ISO>` — pages through `extract-invoice`'s executions from the n8n public API (`GET /api/v1/executions`, header `X-N8N-API-KEY`) back to `--since`, and prints a Markdown table of invoice counts, retries, and average token usage and cost per extraction path, priced from `scripts/lib/pricing.ts` (prices as of 2026-10-30; source in that file). Exits 1 with `N8N_API_KEY is not set (Settings → n8n API)` when the key is missing.
- Regenerate a diagram after you edit its source in `docs/diagrams/`. The diagram tool is [archify](https://github.com/tt-a1i/archify) v3.0.0 or later, which runs on Node.js with no install step; these sources were last checked against v3.2.0.

  Clone it outside this repo, so `pnpm run lint` never scans its files: `git clone --depth 1 --branch v3.2.0 https://github.com/tt-a1i/archify ../archify`. Run the commands from the repo root, because each source's `meta.output` path is relative to it. For the architecture diagram, whose source has type `architecture`:
  1. `node ../archify/archify/bin/archify.mjs validate architecture docs/diagrams/architecture.json --quality showcase --json`, after every edit, until it reports all 9 artifact checks passing with 0 composition errors and 0 warnings.
  2. `node ../archify/archify/bin/archify.mjs deliver architecture docs/diagrams/architecture.json docs/diagrams/architecture.html --quality showcase --json` writes the page. It also writes `docs/diagrams/architecture.delivery.json`, a receipt holding local absolute paths; git ignores it, so never force-add it.
  3. Open the page in a browser, choose **Export**, then **SVG**, and save the download over `docs/diagrams/architecture.svg`, which `README.md` and `docs/architecture.md` embed.
  4. Optionally, `node ../archify/archify/bin/archify.mjs visual-check docs/diagrams/architecture.html --json --out-dir ../archify-evidence` checks the page in a real browser at four desktop sizes and writes its screenshots outside the repo.

## Changing a workflow

1. Design the nodes and expressions against n8n's own node reference and real-world examples, especially for a node you haven't configured by hand before.
2. Edit the JSON in `workflows/` (fixed IDs and credential IDs come from `scripts/manifest.ts`), then run `pnpm run build:workflows` to regenerate any Code node or generated text parameter it touches.
3. Validate the workflow JSON with an n8n-aware validation tool until it reports no errors. It reports "unknown typeVersion 2.8" on Postgres nodes; that's a known false positive to ignore, not a bug to fix — its own node database stops at 2.7, and this project pins Postgres nodes to 2.8 wherever a Query Parameter can carry text (see Conventions).
4. Run `pnpm run setup` to import and publish it against the local n8n instance.
5. Run `pnpm run export` to write n8n's canonical form back to `workflows/` and regenerate Code nodes and generated text parameters again. Commit that exported output, not your hand-edited JSON — the two can differ in server-assigned detail, and the exported form is what actually runs.
6. Run `pnpm run setup` and `pnpm run export` a second time, then `git diff --exit-code workflows/` — a clean diff confirms import and export stay idempotent; a non-empty one means a field is leaking the instance's own state into the committed JSON (extend `export-workflows.ts`'s volatile-fields list).
7. Run the full gate below before committing.

## Recovering stuck events

An event is stuck when its `processed_events.outcome` is still NULL after its run should have finished; the daily summary counts it as unfinished 30 minutes after it arrives. List the stuck events in `psql` (`docker compose exec postgres psql -U "$APP_DB_USER" -d app`):

```sql
SELECT event_id, file_name, received_at FROM processed_events
WHERE outcome IS NULL ORDER BY received_at;
```

Then match each one to its cause:

- **A lost `Record event` response**: the event has no `invoices` row and no `process-invoice` execution. Delete its row, then forward the source email to the inbox again, so Gmail delivers it as new mail: `DELETE FROM processed_events WHERE source = 'gmail' AND event_id = 'stuck_event_id_here' AND outcome IS NULL;`
- **An Information Extractor parse failure**: retrying alone repeats it. Correct `prompts/extract-invoice.md` or `schemas/invoice.schema.json`, run `pnpm run build:workflows` and `pnpm run setup`, then retry the parent's failed execution (`process-invoice`) from n8n's executions list. The retry resumes at the failed extraction call.
- **A wrong label ID**: the run saved the invoice, filed the PDF, and wrote the Sheets rows before the label call failed. A retry reuses the config its run started with, so it fails again. Fix `config/config.json` and add the label to the email by hand. Then read the saved row with `SELECT id, status FROM invoices WHERE source_event_id = 'stuck_event_id_here';` and record the outcome from it, using its `status` (`ok` or `review`) and `id`: `UPDATE processed_events SET outcome = 'ok', invoice_id = 1234567890123 WHERE source = 'gmail' AND event_id = 'stuck_event_id_here';`
- **A call right after `pnpm run setup`**: `setup` already waits 15s past `/healthz` whenever it restarts n8n, which outlasts the publication reconciler's default 10s sync. After any other restart, such as `docker compose restart n8n` or a switch to queue mode, wait the same 15s before you call a workflow. An earlier call can run the previous published version.

## Conventions

- Node 24 LTS, ESM (`"type": "module"`). `tsconfig.json` runs `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, and `allowImportingTsExtensions`, with `noEmit` — there is no build step.
- No `.js` or `.mjs` source files. Scripts are `scripts/*.ts`, run directly with `node scripts/<name>.ts` (Node's native type stripping; no `tsx`). Tests are Vitest files at `tests/**/*.test.ts`. The only JavaScript in the repo is the generated `jsCode` inside workflow JSON.
- CLIs call external programs with `execFile` or `spawn` and an argument array, never a shell string, and guard their entry point with `if (process.argv[1] === fileURLToPath(import.meta.url))` so tests can import their functions without side effects.
- Comments only where intent isn't obvious. A deliberate simplification gets one `NOTE:` line naming its ceiling and upgrade path. A deliberate lint or ShellCheck exception gets a one-line disable comment naming the reason.
- n8n workflow node names are actions (e.g. "Save invoice"), and sticky notes label each section.
- Every node that calls an external service (Gmail, Google Drive, Google Sheets, HTTP Request, Postgres, Information Extractor) sets Retry On Fail with 3 tries and a 1000 ms wait. Execute Workflow nodes never retry, since a retry would repeat a sub-workflow's side effects.
- No Code node is hand-written: each is `export function run(input) { ... }` in `src/nodes/<name>.ts` — pure, no I/O, no clock — compiled by `pnpm run build:workflows`; `pnpm run check` rejects any Code node not listed in `scripts/manifest.ts`'s `CODE_NODES`. Those sources (and `src/lib/`) use the ambient `DateTime` global (`src/globals.d.ts`) instead of importing Luxon, since the Code-node sandbox provides it but has no `require`; ESLint enforces that by banning `node:*` imports, `luxon`, `process`, and `fetch` in `src/nodes/**` and `src/lib/**`.
- Generated text parameters (SQL queries in `db/queries/`, the extraction prompt, the invoice JSON Schema) are copied verbatim into workflow JSON by the same build, addressed by `scripts/manifest.ts`'s `TEXT_PARAMS`. Edit the source file, never the JSON; `pnpm run check` rejects a Postgres query that isn't in that table.
- SQL comments never contain `$n`: n8n formats a query's `$n` placeholders on the client before it ever reaches Postgres, replacing every `$` followed by a digit in the text, comments included. `pnpm run check` rejects a query with one.
- `prompts/extract-invoice.md` contains no `{`, `}`, `@`, or run of 10 or more digits: the Information Extractor treats braces as its own template syntax, and the hygiene check in `pnpm run check` scans the same text once it's generated into workflow JSON. `tests/lib/contract.test.ts` enforces this on every change to the prompt or the schema.
- Postgres nodes are typeVersion 2.8 or later wherever a Query Parameters expression can carry text (checked against `2.45.6`'s source). From 2.8, each `{{ }}` binds exactly one value; 2.5–2.7 still split a string result on commas unless it parses as JSON — a free-text value like a file name containing a comma would become several values. The n8n-aware validation tool's node database tops out at 2.7 and flags 2.8 as unknown; that's the tool lagging the pinned n8n, not a workflow error (see "Changing a workflow" above).
- n8n's Code-node Task Runner (`@n8n/task-runner`) runs generated `jsCode` after setting `Object.defineProperty = () => ({})`, a sandbox hardening measure. esbuild's own IIFE output attaches every named export through that same function, so without a fix every export would silently vanish and `__node.run` would come back `undefined` — see `build-workflows.ts`'s `hardenAgainstFrozenDefineProperty`, covered by a dedicated test that simulates the frozen sandbox. Don't remove it when touching the build.
- `load-config`'s own output is always exactly `{ config }`: `Read config file` discards every caller field before `Parse config` ever runs (checked against the compiled node source and four real executions). Design around this by calling `Load config` on its own branch and merging `{ config }` back onto the caller's own item, rather than expecting it to pass through — see `daily-summary`'s `Attach config to run` merge.
- A workflow that loads config never names an error workflow of itself: n8n runs a sub-execution's own error workflow on failure, just like a top-level run, and its only loop guard is a workflow that names itself as its own error workflow. `error-handler` calls `load-config` to read the team's email address, so if `load-config` named `error-handler` as its error workflow, a missing or unparseable config file would have the two retrigger each other for as long as the failure lasted. `pnpm run check` enforces the exemption by the config loader's fixed id, not by name or file pattern.
- A call to a just-published workflow can still run the previous version for a few seconds after `pnpm run setup` restarts n8n: `/healthz` reports healthy well before the publication reconciler syncs `workflow_published_version` to `workflow_entity.activeVersionId`, which it does on its own schedule (10 s by default, `N8N_WORKFLOW_PUBLICATION_RECONCILE_INTERVAL_SECONDS`) rather than immediately on restart. `pnpm run setup` now waits 15 s past `/healthz` for exactly this reason (see `import-workflows.ts`'s `NOTE:`); that's longer than the default interval, not a guarantee against a slower one.

## Guardrails

- Secrets live only in `.env` (gitignored) and n8n credentials — never in code, workflow JSON, or committed config. No script prints credential data: `setup-credentials.ts` detects which credentials already exist in n8n from a CLI export, never a decrypted one, and only ever logs a credential's name, never its `data`. Credentials go in over stdin and the existing-credentials export (the whole encrypted export — ids, names, types, and encrypted data — of which only the ids are used) comes out over stdout; nothing credential-related touches the host filesystem or the `.n8n-import/` bind mount (a `sh -c` script makes its own temp file in the container's own `/tmp` for each direction and removes it). The Gmail, Google Drive, and Google Sheets OAuth2 credentials' `data` shape was checked against the compiled credential type definitions inside the `n8n` container at `2.45.6`, not by creating a credential in the UI and exporting it decrypted: `GmailOAuth2Api`/`GoogleDriveOAuth2Api`/`GoogleSheetsOAuth2Api.credentials.js` each declare only their OAuth scopes and `extends: ['googleOAuth2Api']`, which itself extends the generic `OAuth2Api.credentials.js` — that base type is where `clientId` and `clientSecret` (both required strings) actually live, confirming the shape all three share.
- `pnpm run setup` skips re-importing a Google OAuth2 credential (Gmail, Drive, Sheets) that already exists in n8n, because `import:credentials` overwrites by id and would otherwise wipe out an interactive Google sign-in. Pass `--force` to overwrite one deliberately.
- The dev harness (`node scripts/dev-call.ts`) requires an `X-Dev-Token` header and is localhost only — this demo has no tunnel. Unpublish its workflow before any production use.
- `scripts/sql/scenario-report.sql` only ever runs as a `SELECT`; `check-scenarios.ts` never writes to the `app` database.
- Test data is invented: suppliers and NITs are fictional, email addresses are on `example.com`, and every printed NIT carries a check digit that deliberately fails the DIAN algorithm. There are no phone numbers and no real people.
- Everything in the repo is in English.
- Database topology: role `$N8N_DB_USER` owns database `n8n`, role `$APP_DB_USER` owns database `app`, and neither can connect to the other's database (`REVOKE ALL ... FROM PUBLIC`). The Postgres superuser exists only to bootstrap those roles in `db/init/`; it is never configured in the n8n container.
- n8n is pinned to `2.45.6`; never move to an unstable `3.x` tag before one is stable. Dependabot's automated updates for `n8nio/n8n` exclude minor and major bumps, because beta and stable releases share plain semver tags.
- Point tooling only at this repo's local n8n instance (`http://localhost:5678`), never another instance.

## Supply-chain hardening

Package management is pnpm, pinned in `package.json`'s `packageManager` to an exact `11.x` version; never move to pnpm 12 (Dependabot's dependency-graph parser does not yet read its default two-document lockfile). `pnpm-workspace.yaml` holds the settings pnpm 11 no longer reads from `.npmrc`:

- `minimumReleaseAge: 4320` — refuses to install any package version (including transitive) published less than 3 days ago, so a newly-compromised release has a window to be caught and pulled before this repo can pull it in.
- `minimumReleaseAgeExclude: []` — pnpm 11 ships a default exclusion list for `n8n`/`n8n-*`/`@n8n/*`; this repo overrides it with an empty one, so no package is exempt from the age gate above.
- `trustPolicy: no-downgrade` — fails an install if a package's trust evidence (provenance/trusted publishing) regresses from an earlier release, or if the pinned pnpm version itself would downgrade that evidence.
- `blockExoticSubdeps: true` — only a direct dependency may resolve from a git or tarball URL; every transitive dependency must come from the registry.
- `strictDepBuilds: true` with `dangerouslyAllowAllBuilds: false` — a dependency's install/postinstall script fails the install unless it's explicitly approved in `allowBuilds`; nothing runs by silent default.
- `engineStrict: true` — a dependency whose `engines` range excludes this repo's Node fails the install instead of warning.
- `allowBuilds` lists only packages a real `pnpm install --frozen-lockfile` proved need their build script, each with a one-line reason. Check `esbuild: true` (its postinstall re-links the platform-specific `optionalDependencies` binary over the `bin/esbuild` JS shim) as the one-entry example; add another only after the same proof.

`tests/supply-chain.test.ts` reads these back through `pnpm config list --json` — pnpm's effective config, not the YAML text — so a misspelled key or a value pnpm silently ignores fails the test. It also asserts `packageManager`'s exact-pnpm-11 shape, that `package-lock.json` doesn't exist, that no tracked file still teaches an `npm` command, and that every Compose `image:` line carries a `@sha256:` digest.

**Updating a dependency:** edit `package.json`, run `pnpm install` (not `--frozen-lockfile`) to update `pnpm-lock.yaml`, run the gate below, and commit both files together. `minimumReleaseAge` will refuse a version published too recently — that's a feature, not a bug to work around; wait it out or pin an older compatible version.

**Landing a security fix younger than the 3-day gate:** a patched version sometimes ships less than 3 days before you need it in. To install it anyway:
1. Add a temporary entry to `pnpm-workspace.yaml`'s `minimumReleaseAgeExclude`, scoped to that one package and version (pnpm accepts `name@version`, e.g. `"esbuild@0.28.3"` — not the bare package name, which would exempt every future version too), with a `#` comment naming the advisory ID and today's date.
2. Run `pnpm install` and merge as usual.
3. Remove the entry once that version is older than 3 days.

`tests/supply-chain.test.ts` asserts `minimumReleaseAgeExclude` is empty, so it goes red the moment step 1 lands — on purpose: the failing test is the reminder to do step 3. Let the test stay red for that one PR's lifetime rather than weakening the assertion for everyone; if that would make CI unmergeable, the simpler rule is to wait out the 3-day gate instead of landing it early, since this repo's own traffic rarely needs the override badly enough to justify a widened test.

**Images** (`compose.yaml`, `compose.queue.yaml`) are pinned `name:tag@sha256:<digest>`, the multi-arch index digest from `docker buildx imagetools inspect name:tag`, so the same reference resolves correctly on both arm64 (local) and amd64 (CI). Dependabot keeps an existing digest current as new builds of that tag are published, but won't add one that isn't there — a tag bump still needs the digest re-resolved the same way and the tag reviewed by hand first.

**CI** installs with `pnpm/setup` (pinned by commit SHA) then `actions/setup-node` with `cache: pnpm`, then `pnpm install --frozen-lockfile`, then `pnpm audit --audit-level=high`.

**The `n8n` job** (`.github/workflows/ci.yml`) is the one job that boots the real stack and proves a workflow executes — both the app Postgres path and a generated Code node — not just that the committed JSON is well-formed. It runs `node scripts/init-env.ts` (CI has no repo secrets, so `.env` is generated, not copied by hand) and `cp config/config.example.json config/config.json`. No credential data ever touches the `.n8n-import/` bind mount (see that directory's own entry in Repo map above), so the job needs no CI-only permissions step for it — the runner's uid (1001) and n8n's own uid (1000) inside the container never need to read or write the same file there. It brings up only `postgres` and `n8n` (`--wait`), runs `pnpm run setup`, then `node scripts/check-dev-response.ts`, and tears down with `docker compose down -v` in an `if: always()` step — CI's volumes are disposable, unlike a local stack's. What CI doesn't run, and why: `pnpm run scenarios` (needs a real Anthropic credential CI doesn't have), `pnpm run cost` (a report over the n8n API's own execution history, not a check — there's nothing for CI to assert), and the queue-mode stack (`compose.queue.yaml`, which adds nothing `check-dev-response.ts` doesn't already prove about Code-node and Postgres execution).

**Dependabot** (`.github/dependabot.yml`) adds a 7-day cooldown to every ecosystem, beyond GitHub's own platform-wide default: `npm` (which also covers the pnpm lockfile) gets semver-tiered days (14 major, 7 minor, 7 patch); `github-actions` and `docker-compose` get a flat `default-days: 7`, since neither has a universal semver convention for "major/minor/patch". Dependabot waits 7 days before proposing a version update, so every version PR is already past pnpm's 3-day `minimumReleaseAge` install gate — it never arrives asking to install a version the gate would still refuse. Security updates are proposed immediately, cooldown-free, since Dependabot never delays those.

## Definition of done

- `pnpm run typecheck && pnpm run lint && pnpm test && pnpm run build:workflows -- --check && pnpm run check` all pass locally — run this full gate before every commit that touches TypeScript. Also run `pnpm run test:db` (with `testdb` up and `TEST_DATABASE_URL` set, see Commands) whenever the change touches `db/schema.sql`, `db/queries/`, or `tests/db/`.
- No secrets anywhere in the diff or git history; `.env` and `config/config.json` are never committed.
- `README.md` (Status, What works now, and the quick start if commands changed) and this file are updated to match what the change actually adds.
- Commits follow Conventional Commits, on a branch named `task-NN-<slug>`.
