# Magdaport AI Invoice Processing

**Demo**

An n8n workflow that reads supplier invoices from Gmail, extracts them with Claude, files each PDF in Google Drive, lists it in Google Sheets, and flags doubtful ones for review.

## Status

In progress: local runtime, toolchain, workflow tooling, the invoice extraction contract, the sample invoices, the SQL the workflow will run, the platform workflows (config loading, error alerts, Drive folder lookup), the `extract-invoice` workflow (text and PDF extraction, routed by path), the `process-invoice` workflow (extraction with a retry, saving, Drive filing, listing each invoice and its line items in Sheets, and labeling the source email), the `intake-email` workflow (a config check and an idempotency gate before any invoice is processed, called once per poll with every new email), the `gmail-entry` workflow (a thin polling entry point that just hands its poll to `intake-email`), and a localhost dev harness for exercising the others without the Gmail poll.

### What works now

- A strict TypeScript toolchain: `typecheck`, `lint`, and `test` scripts.
- The local runtime: Postgres and n8n in Docker Compose, with separate, least-privilege database roles for n8n and the application, and the app database's time zone set to `America/Bogota`.
- The application schema (`db/schema.sql`): `invoices`, `invoice_items`, and `processed_events`.
- A config template (`config/config.example.json`) for the values the workflows will read at runtime.
- Workflow tooling: `npm run build:workflows` compiles Code-node sources and writes generated text parameters (SQL queries, prompts, schemas) into workflow JSON; `npm run check` runs hygiene checks (no pinned data, no literal secrets or ids, every external call retries, every generated value really is generated); `npm run setup` and `npm run export` import, publish, and export workflows and credentials against the local n8n instance. Verified both against the tooling's own fixtures and, now that real workflows exist, end to end: two back-to-back `setup` + `export` rounds produce an identical `workflows/` directory.
- Three platform workflows: `load-config` (reads and parses `/files/config/config.json` into `{ config }`, with Always Output Data on the read step so a missing file reaches the parse step as an item with no binary data and throws instead of stopping silently), `error-handler` (the shared error workflow: loads config, emails the team a plain-text alert naming the failed node, the error, the execution URL, and the Bogota time), and `ensure-folder` (finds or creates a Drive folder by exact name under a parent, always returning a `folder_id`). `load-config`'s happy path and its missing-config failure are both verified offline through the dev harness. `error-handler` and `ensure-folder` are validated (no errors from an n8n-aware validation tool) and published to the local instance, but their Gmail and Drive calls need real credentials.
- A localhost-only dev harness (`workflows/dev-harness.json`, called through `node scripts/dev-call.ts <target> '<json>'`): a token-protected webhook that routes by `target` to a fixed sub-workflow. Verified offline: `load-config` runs end to end and returns `{ config }`; `extract-invoice`'s text path, called with no working Anthropic credential, fails the execution loudly and never returns `status: 'ok'`; `process-invoice` (see below) runs its unreadable-PDF branch end to end against real Postgres and is replay-safe; `intake-email` (see below) runs its full idempotency gate end to end against real Postgres, with the PDF binary crossing an Execute Workflow boundary intact; an unknown target answers `404 {"error":"unknown_target"}`; a request without the dev token is rejected. Localhost only (no tunnel in this demo) and must be unpublished before any production use.
- The invoice extraction contract: `schemas/invoice.schema.json` (the structured-output JSON Schema) and `prompts/extract-invoice.md` (the extraction system prompt), plus the pure TypeScript that turns a model reply into a checked result (`src/lib/invoice.ts`, `parse-reply.ts`, `normalize-invoice.ts`, `validate-invoice.ts`, `file-name.ts`, `util.ts`) and the two Code-node sources: `check-invoice.ts` (used by both extraction paths) and `build-pdf-request.ts` (the vision path's request body, which also refuses to build a request for a PDF whose base64 would overflow the Messages API's 32 MB request limit). All verified offline by Vitest, and now wired into the `extract-invoice` workflow below.
- The `extract-invoice` workflow (`workflows/extract-invoice.json`): routes on `path` to a text branch (an Information Extractor reading already-extracted text through an Anthropic Chat Model sub-node, adaptive thinking, no sampling parameters) or a PDF branch (encodes the PDF to base64, builds a Messages API request with a document block and structured output, and posts it to the Anthropic API with the predefined credential, 120 s timeout), and both branches converge on the generated check that applies the review rules; an unmatched `path` is rejected loudly by a Stop and Error node instead of ending the execution with zero items. Rule failures, and a refusal or truncation on the PDF path, come back as `status: 'review'` (see Limitations for the Information Extractor's different failure mode, by design). Validated (no errors from an n8n-aware validation tool) and published to the local instance; two back-to-back `setup` + `export` rounds produce an identical `workflows/` directory. Verified offline through the dev harness: the text path, called with no working Anthropic credential, fails loudly and never returns `status: 'ok'`.
- Sample invoices for testing and demos (`npm run samples`; `scripts/lib/sample-invoices.ts`, `scripts/lib/invoice-pdf.ts`): six PDFs in `samples/` — two short COP invoices, a ten-item COP invoice spanning three pages, a USD invoice, an image-only scanned invoice, one whose printed total doesn't match its own lines, and a byte-for-byte duplicate — plus the extraction result each one should produce (`samples/expected.json`). All verified offline by Vitest: the five text invoices regenerate byte for byte from their recorded base date, the scanned invoice carries no text layer and renders from a real page image, and every printed Colombian tax ID fails the DIAN check digit.
- The five SQL queries the workflow's Postgres nodes will run (`db/queries/`): recording a Gmail event once, saving an invoice and its line items (replay-safe, and duplicate-safe on a repeated supplier tax ID and invoice number), attaching a Drive link, recording an event's outcome, and the daily summary (a rolling 24-hour window ending at the run's timestamp, so the 18:00 report never loses an invoice that arrives that evening). All verified offline by Vitest against a disposable local Postgres (`npm run test:db`); `save-invoice.sql`, `save-drive-link.sql`, and `record-outcome.sql` are now also wired into `process-invoice` below.
- The `process-invoice` workflow (`workflows/process-invoice.json`) is built to read the PDF's text locally and screen its page count before any AI call runs, call `extract-invoice` on the default model with one retry on a stronger model when a review verdict comes back and a retry model is configured, save the checked record once per event through `save-invoice.sql` (a second save for the same supplier and invoice number comes back as a duplicate instead of a new row), file the original PDF under its year and month Drive folder, append the invoice and its line items to Sheets by key, and label the source email before marking the event's outcome. The generated `Prepare record` Code node (`src/nodes/prepare-record.ts`) turns every extraction outcome — a real check result, or a skip taken before any AI call ran — into one record and builds the Drive file name; verified offline by Vitest. Validated (no errors from an n8n-aware validation tool, aside from the known Postgres 2.8 false positive) and published to the local instance; two back-to-back `setup` + `export` rounds produce an identical `workflows/` directory. **Verified offline** through the dev harness's `process-invoice` target, against real Postgres: a non-PDF attachment saves exactly one `invoices` row (`status: 'review'`, `review_reasons: ['unreadable_pdf']`); sending the same event again adds no second row; the run then stops loudly at the Drive step, since there's no Google credential yet. **Not yet verified live** — built only, pending a connected Google account: the retry on a stronger model, the Drive filing (see Limitations for a duplicate-on-retry risk), the Sheets writes, the email labeling, and the outcome recording.
- The `intake-email` workflow (`workflows/intake-email.json`) holds everything a poll needs done once it has mail: called once per poll with every new email (still as separate items), it loads the config and checks it before anything else runs; splits each email into one item per attachment, keeping only the fields the rest of the workflow needs; keeps only PDF attachments, by MIME type or a case-insensitive `.pdf` name (so one sent as `application/octet-stream` still gets through); records each attachment's event once in `processed_events`; and calls `process-invoice` once per attachment that was newly recorded, continuing with the rest of the batch when one call fails (`process-invoice` has already fired its own error email by then). The generated `Check config` node (`src/nodes/check-config.ts`, over `src/lib/config.ts`'s `checkConfig`) rejects a config with a bad totals tolerance or confidence bound, a non-positive extraction limit, an empty default model, an unrecognized AI effort, a non-string retry model, or a missing label, Drive folder, spreadsheet, tab, or team email, before `process-invoice` or any AI call can run on it; every rule, and the committed `config/config.example.json`, are verified offline by Vitest. Unlike a Gmail-triggered workflow, `intake-email`'s own trigger (`When called`, "accept all data") needs no credential, so it publishes normally. **Verified offline**, through the dev harness's `intake-email` target, against real Postgres: a fresh sample reaches `extract-invoice` and fails loudly on the missing Anthropic credential — not `unreadable_pdf` — which only happens if the PDF binary survived the Set node that drops every other field and the Execute Workflow call into `intake-email`; exactly one `processed_events` row is recorded, with `outcome` left `NULL` and no `invoices` row; sending the same message id and file again adds no second row and never reaches `process-invoice`; a `.txt` attachment is dropped before anything is recorded. **Not yet verified live**: the Drive filing, Sheets writes, and email labeling downstream of `process-invoice` still need a connected Google account (see `process-invoice` above).
- The `gmail-entry` workflow (`workflows/gmail-entry.json`) is now a thin entry point: `Gmail Trigger` polls every minute for mail labeled `Invoices` with a PDF attachment that isn't already labeled `Processed`, `Review`, or `Duplicate`, and `Hand to intake` passes the whole poll to `intake-email` in one call, waiting for it to finish; neither retries, and neither catches a failure, so one goes straight to the error workflow instead of silently repeating `intake-email`'s side effects. **Verified offline:** the workflow JSON's structure and wiring (pinned by Vitest against the real file), validation (no errors from an n8n-aware validation tool), and import/export round-tripping it unchanged. **Not yet published, and nothing in it has run:** the Gmail credential doesn't exist yet, so `npm run setup` holds it back (`hold gmail-entry.json: needs Gmail`) instead of publishing an inactive trigger; the live poll and the handoff itself are deferred to the owner session.
- Credential setup skips a Google OAuth2 credential (Gmail, Drive, Sheets) that already exists, so a re-run can't silently wipe out an interactive Google sign-in.
- CI: lint/typecheck/test/build/check and ShellCheck on one job, `npm audit` and gitleaks on another, actionlint and zizmor on a third, the database tests against a Postgres service container on a fourth; CodeQL (once the repo is public); Dependabot for npm, GitHub Actions, and Docker Compose images.

### Limitations

- **A text-path extraction failure has no automatic recovery.** By design, neither AI call node (`Extract from text`, `Read PDF with Claude`) sets `onError`, so a credential, outage, or Information Extractor parse/schema failure fails the `extract-invoice` execution outright instead of becoming a `review` row. A retry alone repeats the failure: recovery is to correct the prompt or schema, rebuild and publish, then retry the parent workflow's failed execution. Only the missing-credential case has actually been exercised (through the dev harness, see above); an actual Information Extractor parse or schema failure is untested. Upgrading this would route the Information Extractor's error output to a review branch, but only once that branch can also check whether it actually produced output and tell a genuine parse failure apart from a credential or outage error, so an API outage doesn't masquerade as a model review.
- **An `extract-invoice` failure leaves the triggering event unfinished, with no row recorded.** Neither of `process-invoice`'s two calls into `extract-invoice` (`Extract with default model`, `Retry with stronger model`) sets an error output, so a failure there propagates and fails `process-invoice`'s own execution outright: no `invoices` row, no recorded outcome. (They also don't retry — a retry would repeat a sub-workflow's side effects — but a retry wouldn't rescue a deterministic failure like this one anyway.) By n8n's own design, retrying the failed execution from the UI then resumes at the failed node instead of starting over; that resume behavior itself wasn't exercised here. What was exercised offline is narrower: a fresh second call for the same event adds no second `invoices` row — `save-invoice.sql`'s own replay safety, not an execution retry — and the Drive-credential failure past this point (see above). An actual `extract-invoice` failure (an AI credential or parse error) is untested.
- **`Upload PDF` can create a duplicate file on a retry.** Google Drive creates the file on its first request; if the response is then lost, or a later request in the same call errors, a retry (this node's own, or a UI retry of the whole execution) uploads a second copy under the same name, and `Save Drive link` then points the saved invoice at the new copy, leaving the first one orphaned in Drive. The retry stays on regardless, since every external-service node needs one. Upgrade path: look the file up by name in the month folder first, the way `ensure-folder` does for folders, or skip the upload when the saved invoice row already has a `drive_file_id`. Untested here.
- **A lost `Record event` response strands that attachment.** If the INSERT behind `intake-email`'s `Record event` commits but n8n never sees its response, a retry (the node's own, or a UI retry of the whole execution) re-runs the same INSERT, which `ON CONFLICT DO NOTHING` now suppresses; since that's a non-SELECT query returning no rows, n8n's Postgres node reports a bare `{success: true}` item with no `event_id` rather than zero items, so `Keep new attachments` finds no match for it. The attachment looks already recorded even though `process-invoice` never ran for it; it shows up only as unfinished, with no error email. Recovery: delete that event's row from `processed_events`, then forward the source email again so Gmail delivers it as new mail. Verified offline (see above): a replayed attachment produces no second `processed_events` row and no second `process-invoice` call.
- **One failure can trigger more than one alert.** n8n fires a workflow's `errorWorkflow` once for a failed sub-execution and once more for its parent, regardless of how the parent's own Execute Workflow node handles that failure. One invoice failing inside `process-invoice` sends two alerts — from `process-invoice` and from `intake-email`, which called it — even though `intake-email`'s `Process invoice` node is set to continue past that failure so the rest of the batch keeps going. Once `gmail-entry` is live, a failure `intake-email` can't continue past at all (a bad config, say) alerts twice more on its way up through `Hand to intake`: once for `intake-email`, once for `gmail-entry`. Not a bug — the same alert firing again at each level it crosses — but worth knowing before treating alert count as a count of distinct incidents.

## Send the samples

Owner step, once the Gmail, Drive, and Sheets pipeline is live: from the demo Gmail account, send each PDF in `samples/` to that same account, one PDF per email. Send `invoice-06-copy-of-01.pdf` last, after `invoice-01-two-items.pdf` already shows its `Processed` label — it's a byte-for-byte copy of that first invoice, so sending it too soon would make both look like the first arrival. The Gmail filter applies the `Invoices` label to each one as it arrives.

## Quick start

```bash
cp .env.example .env
cp config/config.example.json config/config.json
npm ci
docker compose up -d --wait
npm test
npm run setup   # imports credentials with .env values set; publishes workflows once any exist
```

Fill in the generated secrets in `.env` before bringing up the stack (see `.env.example` for what's required).
